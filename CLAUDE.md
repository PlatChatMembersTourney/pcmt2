## Project

Stats site for the PCMT (Plat Chat Members Tournament), a community Valorant tournament. Static Astro site with React islands, styled with Tailwind v4, deployed as static assets to Cloudflare (`wrangler.json`). Package manager: pnpm.

### Data

- Data lives in `src/data/<season>/<region>/` (e.g. `s3/na`, `showmatch1/na`), one folder per event listed in `src/data/events.json`.
- These files are generated by the bot in `../pcmt-bot` (`build.py`): it combines `matches/individual/*.json` into `matches/matches.json`, then regenerates `player-stats.json`, `standings.json`, `team-map-stats.json` and `agent-stats.json`. Fix data at the source (the individual files) or it will be overwritten.
- Every event works the same way, including `s2/na` (split into individual files in October 2026; it used to be one hand-maintained `matches.json`). Standings rank by match wins, then head-to-head among teams on the same wins, then map and round difference. Upcoming matches get a `winChance` (the bot's Elo prediction, `elo.py`), shown in the match page header.
- The bot's Python writes CRLF line endings; convert its output to LF.
- A match's `combinedStats` totals are built from the per-map stats like the bot's `match.py`: K/D/A/FK/FD summed, ACS/KAST/ADR/HS% weighted by rounds, then `compute_rating`. Rebuild them the same way when fixing per-map lines.
- `PlusMinus` is K − D and `PlusMinus2` is FK − FD.
- Upcoming matches (`completed: false`) have no `veto`, `maps`, `combinedStats` or `mapDetails`, and may have the bot's `winChance`. `Match` is a union of `UpcomingMatch | CompletedMatch` (`types.ts`), so check `match.completed` before using stats. `check.ts` can't tell the two apart (imported JSON only says `completed: boolean`), so `stores/matches.ts` fails the build if a completed match is missing its stats.
- Players have no IDs: they're identified by name, matched across events with `playerSlug()` (`src/utils/playerSlug.ts`), which also gives the `/players/<slug>` URL. Renaming a player means changing every data file they appear in (individual files, `matches.json`, `teams.json`, `player-stats.json`), plus `flags.json` and `../pcmt-bot/puuid_map.json`. S3's spelling is the reference for capitalization.
- Playoff placements (the Placements table under the bracket, `Placements.tsx`) are worked out from the stage's `brackets.json` layout and results, using `playBracket()` (`src/utils/bracket.ts`) - the same helper the bracket drawing uses, so the two always agree: grand final winner and loser, then the teams knocked out in each lower round (upper rounds in single elimination), last round first. Only shown for the stage named "Playoffs".
- A sub is someone who played for a team whose `teams.json` roster they aren't on.
- News articles: one Markdown file each in `src/content/news/<event>/`, with frontmatter checked by `src/content.config.ts` (title, date, author, summary, optional event and match ids). They appear at `/news/<event>/<file>`, on `/news`, and the newest five in the homepage sidebar (`NewsSidebar.astro`). Article text is styled by the `.article` class in `src/styles/article.css` (Markdown can't take Tailwind classes).
- Adding an event: the data folder plus an `events.json` entry is enough for the site, but also add a block for it in `src/data/check.ts` so its files are type-checked.

### Conventions

- Data is loaded in `src/stores/`, one file per data type (`matches.ts`, `teams.ts`, `playerStats.ts`, ...). Import from the specific file you need, so each page only downloads that data. Data is static: plain exports, no state library.
- `src/stores/` is where anything that brings in data lives; `src/utils/` never imports data. `stores/players.ts` is derived (from matches and rosters) and is used at build time only: by the player pages and the search index.
- Search: `src/pages/search-index.json.ts` builds `/search-index.json` at build time; `src/utils/search.ts` matches it in the browser (typo tolerant, prefix matches first); `src/components/Search.tsx` is the box in the header (and first in the mobile menu). Add new kinds of pages to the index there. Easter eggs (an exact phrase that adds a player to the results) are the `easterEggs` list at the top of `search.ts`.
- The header switches between its desktop and mobile layouts at the custom `nav:` breakpoint (900px, in `global.css`), so the desktop layout still fits a half-screen 1080p window.
- Colors: use the theme-aware names from `src/styles/global.css` (`text-main`, `text-muted`, `bg-shade-100`–`400`, `border-line`, `text-pb`, ...), which switch with dark mode on their own, instead of `x dark:y` pairs. Add reused one-off colors to the palette there rather than using arbitrary `[#hex]` values.
- Shared building blocks - use these rather than rebuilding them:
    - `MatchList` (`src/components/matches/MatchList.tsx`): any list of match cards grouped by day.
    - `SortHeader` and `isGroupBoundary` (`src/components/SortHeader.tsx`): headers and group dividers for the TanStack tables.
    - `RatingHeaders.tsx` (`src/components/stats/`): the Toxic/Angus/ACS column headers with their explanations.
    - `section-label` (a Tailwind utility in `global.css`): vlr's red uppercase section labels.
    - `eventById` (`src/stores/events.ts`), `pctFormatter` (`src/utils/format.ts`), `getNews` / `articleDate` (`src/stores/news.ts`).
- Links to the fantasy game (fantasy.pcmt.gg, a separate site): always `FantasyLink` (`src/components/FantasyLink.tsx`: its mint `text-fantasy`, the card icon and ↗). They appear in the event header, upcoming match headers ("Make your pick") and the homepage sidebar (`FantasySidebar.astro`), only for events with `"fantasy": true` in `events.json` - remove that when the fantasy season ends.
- On/off option buttons: use `ToggleButton` (`src/components/ToggleButton.tsx`), passing only spacing classes, so every toggle on the site shares one look.
- Conditional classes: `cx()` from `src/utils/cx.ts` (`class:list` in `.astro` files) instead of string concatenation.
- Anything random (`Math.random()`) must be picked after load with `useRandom` (`src/utils/useRandom.ts`), or the static HTML and the browser disagree (hydration mismatch).
- The same goes for anything time-dependent: relative times ("2d 17h") use `useNow` (`src/utils/useNow.ts`), and dates/times are formatted in `useTimezone()`'s timezone, never the machine's default (the build machine's would end up in the HTML).
- Dark and fun modes are classes on `<body>` (`.dark`, `.fun`), set by the inline script at the top of `<body>` in `src/layouts/Layout.astro` before anything renders; the toggles live in `src/components/Header.astro`.

### Checks

- `npx astro check` should report 0 errors. It needs TypeScript 6, which is pinned in `package.json` (`^6.0.3`) - don't update TypeScript to 7 yet:
    - `@astrojs/check` (0.9.10 as of October 2026) only supports TypeScript `^5 || ^6`. With TypeScript 7.0 installed, `astro check` refuses to run: "astro check does not currently support TypeScript 7.0. To continue using astro check, install TypeScript 6 instead."
    - Astro plans to deprecate `astro check`. Its replacement, `@astrojs/ts-content-mapper` (experimental), type-checks `.astro` files with **TypeScript 7.1 or later**: https://github.com/withastro/astro/tree/main/packages/language-tools/ts-content-mapper#usage
    - Once TypeScript 7.1+ is out (7.0.2 was the latest in October 2026), check whether `@astrojs/check` supports it or switch to `ts-content-mapper`, then update TypeScript and change this note (and the `astro check` mentions here).
- `pnpm lint` runs ESLint (`eslint.config.js`: recommended JS/TypeScript/Astro rules plus the React hooks rules).
- `npx prettier --write src` formats the code. Data JSON is excluded via `.prettierignore`, and line endings are LF (`.gitattributes`).

## Development

When starting the dev server, use background mode:

```
astro dev --background
```

Manage the background server with `astro dev stop`, `astro dev status`, and `astro dev logs`.

Node is managed by pnpm (`pnpm runtime`); an older Node elsewhere on `PATH` (e.g. nvm's) may be found first, so put pnpm's `bin` folder first.

Libraries loaded with a dynamic `import()` (like `brackets-viewer` in `Bracket.tsx`) need an entry in `optimizeDeps.include` in `astro.config.mjs`, or the dev server fails to load them with "504 Outdated Optimize Dep".
